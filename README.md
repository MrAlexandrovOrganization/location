# Location

Go-сервис хранения геопозиции с PostgreSQL.

## Версии и сборка

Go задаётся в `go.mod`, образы — в `makefiles/versions.mk`. `make versions` показывает
итоговые значения. Make экспортирует их в Compose и Dockerfile; отдельный
checkout соседних проектов для получения версий не нужен.

- `make build` — собрать Go-бинарник.
- `make compose-build` — собрать образ.
- `make test` — тесты.
- `make install` — зависимости; `make format` — форматирование; `make check` — тесты, vet, форматирование и Compose.
- `make migrate` — явно применить миграции; обычный запуск проверяет схему без изменения.
- `make run` — локальный запуск; PostgreSQL задаётся через `POSTGRES_URL`, остановка — Ctrl+C.
- `make up` / `make down` / `make logs` — управление сервисами.

Go в CI также читается из `go.mod`. Меняйте каждую версию только в её источнике.

## Доставка образов из CI

Рекомендуемый путь релиза: собирать образ после проверок в CI и разворачивать
опубликованный образ по digest. На VM не пересобирать приложение из checkout:
так запускается тот же артефакт, который прошёл проверки.

CI выполняет существующие проверки, затем `make image-build` собирает все собственные
образы из build-секций Compose без runtime-секретов и соседних checkout.
Push main публикует **эти же** образы в GHCR через `make image-publish`.
Тег содержит SHA, run ID и attempt; artifact `image-release` содержит digest manifest.
Платформа — `linux/amd64` (текущая VM). На PR публикации и доставки нет.
Версии build args по-прежнему приходят из Make, определения сборки — из Compose.

SSH CD передаёт SHA, manifest и временный token в `make ci-deploy`.
Эта цель из `makefiles/ci-deploy.mk` под одной блокировкой проверяет чистый main,
отклоняет устаревший workflow, fast-forward обновляет checkout до проверенного SHA,
временно авторизует Docker в GHCR и вызывает `make image-deploy` из нового Makefile.
Сначала скачиваются все образы, затем `image-activate` сохраняет подготовку/миграции
этого проекта и запускает Compose с `--no-build --pull never --wait`.
Доступ к registry удаляется и при ошибке. `ci-deploy` требует переменные
`DEPLOY_SHA`, `IMAGE_MANIFEST_B64`, `GHCR_USER`, `GHCR_TOKEN` из окружения;
не передавайте token аргументом Make или команды.

Короткий SSH-шаг делает fetch и загружает только `makefiles/ci-deploy.mk` через
`git show` из SHA этого workflow. Поэтому первый деплой работает и со старым
checkout без новой цели. Загруженный файл сам проверяет актуальность SHA и повторно
делает fetch после захвата блокировки; параллельные доставки не обновляют checkout
во время активации. Обычные `make up` и существующие `make deploy` сохраняют
свои прежние контракты; для CI служит отдельная цель `ci-deploy`.

Для CI разрешите GitHub Actions запись Packages. Новые GHCR packages по умолчанию
private; настройте наследование доступа от этого репозитория. Автоматический CD
использует временный `GITHUB_TOKEN` с `packages: read` и временный Docker config,
который удаляется после SSH-шагa. Для ручной доставки нужен отдельный read-only
доступ (`read:packages`) или публичный package; приложение секреты получает только на VM.
VM нужны Python 3.9+, Make, Docker Compose с `--wait`, Git и flock для SSH CD.

`.images/current.json` хранит последний успешный manifest, `previous.json` — предыдущий.
Для отката сначала согласуйте совместимость БД и конфигурации, верните checkout
к `revision` выбранного manifest и выполните `make image-deploy IMAGE_MANIFEST=...`.
Автоматического отката БД/образов нет; не удаляйте нужные digests в GHCR.
`make up` остаётся локальной сборкой из исходников: на VM для релиза используйте
`image-deploy`; `logs`/`ps` читают те же контейнеры. Сторонние образы не пересобираются,
их версии остаются в конфигурации проекта. Внешний registry-кеш между CI runs пока
не настроен. Успешный build не подтверждает runtime: проверяйте readiness и сценарий
сервиса после доставки.

Для диагностики и явных CLI-операций из активного образа используйте
`make image-compose IMAGE_ARGS='ps'`, `IMAGE_ARGS='logs -f'` или
`IMAGE_ARGS='run --rm SERVICE COMMAND'`. Последняя команда автоматически
запрещает сборку и pull. Она подходит для явных миграций/CLI, которые раньше
запускались через локальный Compose-образ. После неуспешной активации
`.images/requested.json` сохраняет manifest попытки; `current.json` остаётся
последним успешным и не гарантирует, что частичный rollout откатился.

Ручной `image-deploy` использует тот же host lock, что SSH CD; не запускайте
обходные Compose-операции одновременно с доставкой. При первом переходе на GHCR
`previous.json` ещё отсутствует: сохраните прежние локальные образы и конфигурацию
для восстановления по runbook до первого релиза.

## Container names and monitoring

Containers are `location` and `location-postgres`. Docker clients use service names;
metrics use the `location-metrics` alias and a stable `service: location` label.
Set `GRAFANA_LOCATION_DB_ADDRESS` to the address reachable from Grafana:
`location-db:5432` on the shared Docker network, or the existing VM endpoint
when Grafana runs on another host. Provisioning never derives the address from
the container name. `CONTAINER_NAME_PREFIX` isolates additional local/CI stacks.

## Структура Compose

Файлы Docker Compose находятся в `compose/`; основной файл — `compose/docker-compose.yml`.
Команды запускайте из корня проекта через Makefile: он задаёт `--project-directory`
на корень checkout. Build contexts, bind mounts, `env_file` и секреты остаются
относительными к этому корню; имена Compose project, сервисов, сетей и томов сохранены.
При явном вызове Docker используйте `docker compose --project-directory . -f compose/docker-compose.yml ...`.
Если в приватной `.env` или окружении задан `COMPOSE_FILE`, добавьте `compose/`
к прежним именам файлов, сохранив прежний набор overlays и порядок. Для плавного
перехода Make также распознаёт прежние короткие имена, если файлы уже перенесены.
Не меняйте project name и не удаляйте прежние тома для переноса файлов.

## Android и доставка без потери подтверждения

Локальный независимый Android-проект — `android/location-app` в рабочей папке
projects. Нативный клиент использует существующий HTTP-сервис; HTTP сохранён
для совместимости с notes-bot и простого мобильного клиента без второго API-стека.
Публично старый API не открывать: он не имеет аутентификации и доступен только
из внутренних сетей/tailnet. Мобильный маршрут имеет отдельную write-only авторизацию.

`PUT /mobile/locations/{canonical-uuid}` принимает `Authorization: Bearer TOKEN`
и JSON с обязательными `latitude`, `longitude`, `accuracy`, `recorded_at` (RFC3339).
Сервер назначает `source=android`, `date` из UTC-времени измерения. Тело до 4096 байт.
Точка может быть старой: офлайн-история не заменяется временем загрузки.
Ответ 200 `{"id":"...","stored":true}` отправляется после записи в PostgreSQL.
Повтор с тем же UUID и теми же измерениями возвращает подтверждение без второй
строки. Другие данные под существующим ID дают 409 и не переписывают исходную
точку. 400/401/409/503 не разрешают удаление локальной очереди. Координаты и
bearer не выводятся в логи. Случайный bearer проверяется по SHA-256 в constant time;
`MOBILE_TOKEN_SHA256` содержит только его hex-хэш. Пустая настройка отключает маршрут.

Сгенерировать ключ и локальную инструкцию без вывода токена в терминал:

```sh
make mobile-device
```

Секрет и инструкция появятся в игнорируемом `secrets/mobile-device.txt` (0600).
Файл `secrets/mobile.env` содержит только `MOBILE_TOKEN_SHA256`: добавьте эту
настройку в приватную серверную `.env`, не заменяя остальные значения.
Токен вводится на телефоне. Не публикуйте эти файлы. Сейчас предусмотрен один
bearer; его замена требует обновления телефона и не очищает его очередь.

Миграция `004_android.sql` добавляет enum, сохраняя исторические строки и UUID.
CI activation сначала поднимает существующую PostgreSQL, явно запускает `location
migrate` из нового digest, затем приложение и проверяет `/readyz`. Миграции и
история выполняются под advisory lock в транзакции; существующие имена в
`schema_migrations` сохраняются. Удалять enum/историю при откате не нужно.
`/healthz` — liveness, `/readyz` проверяет PostgreSQL. Для ручного локального
запуска сначала `make migrate`. Для прежнего локального `make up` миграцию нужно
выполнить явно; автоматическое изменение схемы при обычном старте убрано.

Grafana продолжает читать ту же `locations` и `recorded_at`: существующий
дашборд Location в notes-bot показывает Android-точки без смены datasource.
Фильтр `NOT hidden` и прежняя эвристика невозможной скорости сохраняются.
Подтверждение сервера означает commit, а не наличие независимого бэкапа.
Перед релизом сохраняйте `pg_dump` вне VM; хранение первоначального миграционного
архива само по себе не доказывает регулярные бэкапы новых точек. Проверяйте
восстановление дампа в отдельную PostgreSQL, включая количество точек/последнее
`recorded_at`, роль Grafana и подключения. Не восстанавливайте поверх работающей БД.

Синтетическая интеграционная проверка применяется только к отдельной тестовой БД:
`TEST_DATABASE_URL=... go test -race ./internal/repository`. Она проверяет сохранение
старых Telegram-точек, явные миграции, повтор и конфликт UUID; production URL ей
передавать нельзя. Обычный `make check` не подключается к рабочей БД.

## Постоянный блэклист координат

В PostgreSQL находится таблица `public.location_blacklist`, доступная для
редактирования через DBeaver под пользователем `location`. Правила изначально
пустые: разовая ошибка в истории не добавляется в постоянный блэклист автоматически.

| Поле | Значение |
| --- | --- |
| `id` | Генерируется базой, вручную не заполнять |
| `latitude`, `longitude` | Центр исключения, десятичные градусы |
| `radius_m` | Радиус в метрах; по умолчанию `0` — строгое совпадение обоих чисел |
| `enabled` | Включено по умолчанию; `false` отключает правило |
| `note` | Произвольная заметка, например причина исключения |
| `created_at` | Время создания, заполняется базой |

Допустимые координаты: широта −90…90, долгота −180…180; радиус 0…100000 м.
Для небольшого скопления можно задать, например, 50–100 м. Проверка расстояния
использует сферическую формулу с радиусом Земли 6371000 м и работает через
меридиан ±180° и возле полюсов; PostGIS не требуется. Радиус — географическая
дистанция, он не увеличивается на `accuracy` входящей точки.

Чтобы добавить точное совпадение из существующей строки без округления координат,
замените `ID_НЕВЕРНОЙ_ТОЧКИ` и выполните:

```sql
INSERT INTO public.location_blacklist (latitude, longitude, note)
SELECT latitude, longitude, 'Постоянно неверная координата'
FROM public.locations
WHERE id = 'ID_НЕВЕРНОЙ_ТОЧКИ';
```

После сохранения/commit правила PostgreSQL в той же транзакции выставляет
`hidden=true` всем совпадающим историческим точкам. Триггер на `locations`
скрывает новые точки и повторные изменения координат/`hidden`, в том числе
прямые SQL-записи из DBeaver. Все исходные координаты и UUID сохраняются.
Пока действует правило, вручную снять `hidden` у совпадающей точки нельзя.
Для ручных записей используйте штатный уровень изоляции `READ COMMITTED`:
изменения правил и запись точек согласованы общими/эксклюзивными transaction
advisory locks. Они берутся до блокировки строк; параллельные обычные вставки
точек не сериализуются друг с другом. Изменение правил может ждать завершения
открытых транзакций с записью точек.

Отключение/удаление или перенос правила не раскрывает ранее скрытые точки:
сохраняются ручная очистка, фильтр скорости и прежние результаты блэклиста.
Если нужно вернуть конкретные точки, сначала отключите соответствующее правило,
затем явно снимите `hidden` у выбранных UUID. Включение правила снова применит
его к истории. Результат не зависит от перезапуска сервиса и не кешируется.

Backend получает фактический `hidden` через `INSERT … RETURNING`, поэтому
ответы API и счётчики сохраняют результат триггера. Повтор UUID остаётся
идемпотентным, а blacklisted точки исключаются из опоры фильтра скорости.
Grafana продолжает использовать существующий `WHERE NOT hidden`; обновление
Android/Telegram-клиентов или дашборда не требуется.

Схема и триггеры принадлежат миграции `005_location_blacklist.sql` и применяются
явной стадией `location migrate` из проверенного CI image digest. Самостоятельно
создавать эту таблицу до миграции не нужно. Старые миграции не изменяются;
перед доставкой сохраняется внешний дамп, пустая таблица не меняет историю.
Предыдущий бинарник может работать с добавленной схемой, но его ответ `hidden`
не учитывает результат триггера — для API используйте новую версию.

Проверки реальной PostgreSQL запускаются отдельно от обычного `make check`:

```sh
make test-db-up        # изолированная location_test, loopback:55439, tmpfs
make test-integration  # миграции, legacy-данные, retry, exact/radius, backfill,
                      # отключение, rollback, валидация и два порядка concurrent writes
make test-db-down      # удаляется только контейнер с тестовой меткой
```

CI вызывает эти же цели и останавливает тестовую БД также при ошибке.
`TEST_DATABASE_URL` можно задать явно; проверка требует имя БД `location_test`
и очищает её `public` — рабочую БД использовать нельзя. В тестах только
синтетические координаты и отдельное хранилище, без рабочих точек/токенов.

## Автоматическое подтверждение выбросов

Фильтр сравнивает измерение с видимой опорой, записанной **раньше времени
измерения**, без сброса на границе UTC-даты. Более новые точки офлайн-очереди не
становятся его опорой. При ошибке чтения опоры запись завершается ошибкой:
мобильный клиент сохраняет UUID и повторяет доставку.

Обычное превышение скорости сразу скрывает точку, но само по себе не
создаёт постоянное правило. Backend учитывает новые отказы фильтра в
`location_outlier_observations`. Для обычных отказов автоматическое **точное**
правило (`radius_m=0`) создаётся для текущей координаты при всех условиях:

- В пределах 100 м накоплено минимум пять скрытых отказов фильтра скорости.
- Они относятся минимум к трём разным календарным дням `Europe/Moscow`.
- В этих 100 м нет ни одной видимой записи, включая исторические посещения.
- Координата не совпадает с существующим правилом, в том числе отключённым.

100 м — окрестность для проверки повторов, а не радиус создаваемого правила.
Пороги заданы в `internal/repository/outliers.go`. Это консервативная эвристика,
а не доказательство физической невозможности координаты: правила с заметкой
`auto_speed_confirmed` можно проверить и отключить в той же таблице блэклиста.
Отключённые вручную правила автоматика не включает и не дублирует.

Для явно невозможного скачка от устойчивой свежей опоры есть быстрый путь:
расстояние не меньше 5 км и превышение допустимой скорости после вычета
погрешностей обеих точек. Опора не старше двух минут, с точностью не хуже 250 м;
её подтверждают ещё две видимые точки того же provider за предыдущие три минуты,
в пределах 250 м и с общей длительностью наблюдения минимум 30 секунд. Такая
координата может получить точное правило сразу, без ожидания трёх дней. Проверки
видимых посещений и отключённых правил остаются обязательными.

Для экстремального скачка действует дополнительный быстрый путь: расстояние
не меньше 5 км, скорость после вычета погрешностей выше **500 м/с (1800 км/ч)**
и одновременно выше пятикратного `MAX_SPEED_MS`. Здесь достаточно двух
согласованных точек опоры вместо трёх: последняя не старше двух минут, обе с
точностью до 250 м, в пределах 250 м друг от друга и с интервалом от 30 секунд
до трёх минут. Причина — `extreme_jump`. Одиночная опора, короткая серия дублей,
скрытые или неточные измерения не дают такого подтверждения. Проверки прежних
видимых посещений и вручную отключённых правил сохраняются. Обычные превышения
скорости по-прежнему требуют прежнего подтверждения; пороги для них не снижены.
Миграция `008_extreme_jump_reason.sql` добавляет диагностическую причину, не
пересматривая историю и не меняя исходные измерения.

Старые `hidden` не преобразуются в доказательства: среди них есть ручные скрытия
и реальные поездки. Учёт новых отказов начинается после доставки миграции
`006_confirmed_outliers.sql`; существующие координаты и видимость не меняются.
Точка, наблюдение и правило сохраняются одной транзакцией под блокировкой
изменения правил. Повтор UUID не увеличивает число наблюдений; ошибка любой
части откатывает всю запись. Прямые SQL-вставки не классифицируются автоматически.
При удалении точки удаляется её наблюдение; удаление опорной точки не удаляет
наблюдения других измерений.

Отключение ошибочного правила сохраняет старую историю скрытой. Чтобы вернуть
конкретную поездку, сначала отключите совпадающие правила, затем снимите `hidden`
только у проверенных UUID. Добавленная схема совместима с предыдущим бинарником;
откат образа прекращает накопление новых наблюдений, сохраняя правила и историю.

## Качество и независимые источники

Мобильный API дополнительно принимает необязательный `provider`: `gps`, `network`,
`passive`, `fused`, `unknown`. Старые клиенты остаются совместимы. Это диагностическая
метаинформация, а не часть идентичности UUID: повтор старой очереди с добавленным
provider подтверждается без изменения ранее сохранённых измерений. Поля `provider`
и `quality_reason` хранятся в БД; прежние JSON-ответы чтения не меняются.

Сетевые точки продолжают свою сетевую последовательность и не сравниваются с
одним случайным GPS-скачком. Для GPS предпочтительна видимая сетевая опора не
старше двух минут с точностью до 250 м. Без такой поддержки одиночный перенос
на 5 км и больше сохраняется скрытым как `uncertain_jump`, даже если большая пауза
делает скорость формально допустимой. Он не становится следующей опорой и не
считается доказательством для постоянного блэклиста. Сетевая фиксация с точностью
до 250 м позволяет восстановить позицию после реального длительного разрыва GPS.
Без сетевых данных реальный большой разрыв тоже может остаться сомнительным;
такие записи сохраняются для проверки, а не удаляются и не блокируются навсегда.

Точность хуже 500 м даёт `poor_accuracy`: запись скрыта, не является опорой и не
накапливает доказательства. У обычного отказа скорости причина `speed`, у быстрого
подтверждённого скачка — `corroborated_jump`. Погрешность не доказывает корректность
координаты. Ни сглаживание, ни привязка к дороге не заменяют проверку источников.

Миграция `007_location_quality.sql` добавляет только метаданные и индекс, не
пересматривая историю. Для новых возможностей источников требуется Android APK
1.1.0: он сохраняет GPS и сетевые измерения независимо и назначает UTC-время по
системным часам телефона минус монотонный возраст фиксации. Уже сохранённая очередь
сохраняет исходные UUID, измерения и время; её содержимое не переписывается.

## Приём исходных измерений и обновления Android

Начиная с APK 1.2.0 клиент только собирает и надёжно доставляет данные. Он не
отбрасывает старые/повторные/неточные callback и не вычисляет исправленное время.
`PUT /mobile/measurements/{uuid}` использует прежний mobile bearer, принимает JSON
объект до 64 KiB и возвращает stored=true только после commit. Транспортные ошибки
(JSON/размер/авторизация/UUID) дают 4xx. Неверные измерения сохраняются скрытыми
с raw_payload и причиной, поэтому не блокируют очередь безвозвратно. Повтор UUID
с тем же исходным телом идемпотентен; другое тело даёт 409. Старый API и старые
очереди APK 1.0/1.1 продолжают работать без изменений.

`internal/adapter` содержит отдельные адаптеры Android и Telegram. HTTP handlers
выбирают адаптер и передают общий CreateInput в service.Save. Общий сервис не
знает форматов фронтендов. Android timestamp рассчитывается на сервере из UTC
получения callback минус монотонный возраст измерения; provider_time_ms остаётся
в raw_payload. Возраст более двух минут даёт stale_measurement; неверные поля —
invalid_measurement. Повтор монотонной метки в рамках installation/boot/provider —
duplicate_measurement, более ранняя — out_of_order_measurement. При недоступном
boot_count используется collection_session_id. Эти записи сохранены скрытыми,
не становятся опорой и не создают доказательств для blacklist. Порядок проверяется
под транзакционной блокировкой, после блокировки правил; повтор UUID не создаёт
дополнительного наблюдения.

Telegram frontend передаёт исходный location и message_date/edit_date в
`POST /telegram/measurements` (внутренний API, как прежний POST /locations).
Адаптер использует edit_date для live update, вычисляет логический день из
переданного контекста timezone/day-start и назначает устойчивый UUID по update.
Мобильный Android-адаптер сохраняет прежнюю UTC-дату. Общая проверка качества,
скорости, опоры и blacklist одинакова для обоих источников. Notes-bot обновлять
после backend. Миграция 009 сохраняет историю; received_at у старых строк NULL,
а у новых — время приёма БД. raw_payload — исходные поля JSON, raw_sha256 — хэш
исходного тела запроса. При неверных координатах нормализованные столбцы могут
содержать 0; это hidden/invalid_measurement, а исходное значение остаётся в raw.

`GET /mobile/app-update` и `/mobile/app-update/{sha256}.apk` требуют mobile bearer;
без релиза manifest даёт 204. Разрешён только текущий APK, пути/redirect не
принимаются. В `.mobile-releases/` (игнорируется Git) лежат APK/current.json и
previous.json; каталог монтируется read-only в контейнер. Публикация из Android
CI использует отдельный SSH key с restrict и forced command:
`python3 /home/maxim/projects/backends/location/scripts/receive-mobile-release.py
--directory /home/maxim/projects/backends/location/.mobile-releases`.
Единственная принимаемая SSH команда — publish-mobile-release. Receiver ограничивает
поток 64 MiB/180 сек, проверяет хэш/размер/версию/certificate identity и переключает
manifest атомарно. Бинарник на VM не собирается. Откат выпускается с большим
versionCode. Ключ подписи никогда не нужен backend и не хранится на VM.
